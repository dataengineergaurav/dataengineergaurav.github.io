# Taste
- Wants a plan laid out (architecture, files to add/modify, verification steps) before implementation — explicitly asks to "see your plans" rather than jumping to code. Confidence: 0.6
- Prefers a pull-request workflow with human-in-the-loop review over direct pushes to production; for the weekly progress pipeline he wanted a PR for review/merge rather than pushing straight to production, and when offered a choice between `git push origin master` and the PR path for the website repo he chose "open the PR and merge". Confidence: 0.8
- Wants changes split into multiple logically-scoped, atomic commits (one per independent concern) rather than a single bulk commit; agreed to splitting a pre-existing fix and a new feature into separate commits. Confidence: 0.55
- Wants output framed as meaningful outcomes/capabilities rather than raw activity metrics — explicitly "do not equate commits with progress". Confidence: 0.6
- Wants evidence-backed, non-exaggerated writing: no invented accomplishments, no claims of production usage or performance gains without supporting evidence, no secrets or private-repo details; prefers concrete technical details, real numbers, and links to source artifacts. Confidence: 0.7
- Prefers reusable agent skills/playbooks authored into the repo alongside the pipeline they drive, rather than one-off scripts, and decomposes a workflow into several focused named skills (collector, analyzer, writer, editor, orchestrator) instead of one monolith. Confidence: 0.75
- Values distinctive, intentionally-crafted design flourishes and prefers fixing their mechanical glitches (e.g. awkward animations/blank beats) over stripping the feature out — chose to keep the pinned Work ledger and Voices reveal rather than drop them. Confidence: 0.4
- Wants UI/UX guidance grounded in human behavior, usability heuristics, and established interface patterns — asked for a skill that explicitly "supports human behavior, usability, and interface patterns" rather than visual craft alone. Confidence: 0.6
- For a broad knowledge domain, prefers one skill with on-demand reference files (progressive disclosure: a short SKILL.md routing to `references/*.md`) over several overlapping sibling skills — confirmed one `ui-ux` skill with three references instead of three separate skills. Confidence: 0.5
- Prefers skills that explicitly defer to a neighbouring skill for adjacent concerns rather than duplicating them (e.g. UI-UX defers palette/type/layout/motion/voice to the `design` skill and reuses its severity scale). Confidence: 0.5
- Expects a skill he just asked for to be applied to the real project right away ("use such skills to improve the web design and user experience of the website") — authoring a playbook is only useful to him as a tool run against live code, not as standalone documentation. Confidence: 0.5
- Communication for tooling/git work is ultra-terse and imperative ("commit and push", then "push", then "open the PR and merge"), with no elaboration — he expects the agent to just execute the operation rather than receive multi-step manual instructions or re-litigated caveats. Confidence: 0.6
- Prefers the `gh` CLI as the tool for GitHub operations (creating/merging PRs) rather than raw git verbs or other mechanisms — explicitly instructed "use gh commands instead". Confidence: 0.6
- Comfortable issuing broad, outcome-level mandates over a whole surface (e.g. "improve the design and UX of the website") and letting the agent run its own review passes and fix the findings without a per-finding approval gate. Confidence: 0.4
